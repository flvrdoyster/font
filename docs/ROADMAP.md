# 도깨비DNR 고딕 — 로드맵

파생 방향 확정 이후의 작업 계획. 3개 페이즈로 진행한다.

## 공통 설계 (전 페이즈 관통)

- 웨이트 2종, 둘 다 정적 폰트(픽셀 폰트는 보간이 무의미). **Light는 Regular에서 기계적으로 파생** — 별도 수작업이 아니다.
- 획 문법
  - **Regular**: 세로 줄기 2px / 가로 바·크로스바 1px / 대각선 1px 계단
  - **Light**: Regular에서 **세로 줄기만 1px로** 줄임 → 전 획이 균일 1px
- 수직 밴드
  - 한글: row 1–13 (13행, 상하 1px 여백)
  - 라틴: cap row 2 ~ baseline row 12 (11행), x-height row 6~, 디센더 row 13–15
- 제작 방식: [gensei-pc98](../../gensei-pc98) 저장소의 `docs/bios/font.bmp`(PC-98 BIOS 폰트, 16px 그리드)에 해당 글자가 있으면 그 골격을 참조해 위 문법으로 재작성. 원본에 아예 없는 글자(₩ 등)만 신규 드로잉.
- **에디터 구조**: `tools/pixel_editor.html`은 상단 탭으로 **Regular / Light**를 분리한다.
  - 저장 파일도 완전히 독립: `tools/glyphs_regular.json`(라틴, 2px) / `tools/glyphs_light.json`(한글 조합형, 1px). 같은 글자가 나중에 두 웨이트 다 필요해져도 충돌 없음.
  - `scripts/editor_server.py`의 모든 글리프 엔드포인트(`/api/glyphs`, `/api/text`, `/api/build`)는 `?weight=regular|light` 파라미터로 대상 파일을 가른다. `/api/original`(참조 오버레이용 원본 비트맵)은 웨이트 무관 — 항상 도깨비 디나루 2px 원본.
  - 빌드(`build_ufo.py` 등)는 현재 **Regular 전용**. Light는 아직 빌드 파이프라인이 없음(Phase 2 실행 후 마련).

## Phase 1 — Regular 웨이트 완성

- 범위: 영문 소문자 **반각 a–z + 전각 ａ–ｚ** (52자)
- 신규 설계 요소: 소문자에서 처음 쓰는 x-height·어센더·디센더
  - x-height 몸통: a, c, e, m, n, o, r, s, u, v, w, x, z
  - 어센더(cap 라인까지): b, d, f, h, k, l, t
  - 디센더(row 13–15 사용): g, j, p, q, y
- 순서: 반각을 먼저 만들어 손으로 다듬고, 전각은 PC-98 소문자 골격으로 같은 방식 파생 (대문자 작업 때와 동일 패턴)
- 완료 기준: 라틴·숫자 전 범위(대/소문자 × 반/전각) 완성 = 약물·가나를 제외한 Regular 웨이트 사실상 완성

## Phase 2 — Light 웨이트 → PC-98 BMP

- 범위: **전체 폰트** — 한글 11,172자 + 라틴/숫자 전부 (Light 웨이트 자체는 범용 산출물)
- 방식: Regular의 세로 2px 줄기를 1px로 기계적으로 얇힘
  - 라틴/숫자: 커스텀 글리프에 적용 (상대적으로 쉬움)
  - 한글: 원본 도깨비 디나루 비트맵 11,172자에 일괄 적용 (핵심 작업)
- **thinning 알고리즘 준비 완료**: [`tools/thin_vertical.py`](../tools/thin_vertical.py)
  - 인접 컬럼 쌍이 최소 2행 이상 이어지는 세로 런을 찾고, 그중 **폭이 정확히 2px인 행만** 오른쪽 컬럼을 드롭
  - 가로 바(1px)·ㅇ/ㅎ 원형 자모의 3px+ 페싯은 폭 조건에 안 걸려 자동으로 보호됨 (처음엔 페싯이 비대칭으로 반쪽만 얇아지는 결함이 있었는데, "정확히 2px" 조건으로 고침)
  - 라틴(A/H/a/o/m) + 한글 스트레스 샘플(한글도깨비이응왕뚫옳 — 원·대각선·밀집 받침)로 검증 완료
  - 부수 효과: ㅇ/ㅎ 원이 "위아래 캡 굵게·옆면 얇게"로 자동 수렴 — 우리가 손으로 만든 라틴 O와 같은 디자인 언어라 일관성 있음
- **gensei-pc98 실제 소요량 확인**: 전체 11,172자가 아니라 **전각 완성형 2,350자(KS X 1001) + 반각 한글 98자**만 필요 (`tools/charmap.json` 기준). ASCII 반각 94자는 게임 원본 폰트를 그대로 씀 — 우리 작업 불필요.
- 남은 리스크: 지금까지는 표본 검증만 마쳤고 11,172자 전체 실행은 아직 안 함. 전체 실행 후 육안 표본 QA로 깨진 글자 스크리닝 필요 (특히 ㅇ/ㅎ 포함 글자, 받침 밀집형)
- 산출물: Light 웨이트 TTF + **gensei-pc98용 `font.bmp`** (2,350+98=2,448자만 추출해 SJIS→ku/ten 좌표로 배치). PC-98 원본이 1px 획 계열이라 무게가 맞음
- 완료 기준: Light 웨이트 + PC-98 BMP 납품

## Phase 3 — 약물/기호 + 가나 (장기)

- 산세리프 스타일로 재작성
  - 약물/기호: 원본에 있는 것은 PC-98/원본 골격 참조, 결손된 것(₩, —, •, © 등 `coverage_report.py` 목록 27자)은 신규 드로잉
  - 가나: 반각 가타카나 63자 완전 신규, 전각 히라가나/가타카나 168+자는 원본 필체형 → 한글 톤의 기하학적 스타일로 재설계
- 규모가 커 Regular/Light 골격이 끝난 뒤 별도 진행. 완료 시 두 웨이트 모두에 반영

## 병행 트랙 — 한글 재설계 (완성형 → 조합형)

Phase 1/2/3와 별개로 진행하는 장기 트랙. Phase 2(Light 웨이트)는 원본 도깨비 디나루
비트맵을 그대로 시닝하는 것이라 이 트랙과 무관하게 계속 진행한다.

- **목표**: 한글을 원본 그대로 두지 않고 우리 스타일로 재설계. 최종 범위는
  **KS X 1001 완성형 2,350자** (11,172자 전체 아님 — 2,350은 gensei-pc98 소요량과도 겹침)
- **방식**: 낱개로 2,350자를 다 손으로 그리지 않는다.
  1. **완성형 스타터 세트**(소규모, 손으로 직접 그림) → 초성·중성·종성 부품과 조합 규칙(원칙) 확립
  2. **조합형**(부품 조합 생성) → 원칙을 초성 19 × 중성 21 × 종성 28 부품에 적용해 나머지 생성
  - 11,172 = 19×21×28은 조합 가능한 전체 공간 그 자체 (조합형의 정의상 상한). 2,350은 그중 KS X 1001이 추린 실사용 부분집합.
  - 부수 효과: 부품(약 67개)만 확립되면 Phase 2 시닝도 11,172개 글리프 각각이 아니라 **부품 단위로 한 번만** 돌리면 되어 훨씬 안정적 — 두 트랙이 나중에 합류할 수 있음
- **스타터 세트 (38자, 초성 19/19·중성 21/21 전부 커버)**:
  `다람쥐헌쳇바퀴에타고파` (팬그램, 11자) + `꿈나딸물산씨빵짝애야얘여예와왜외요워웨유그의값닭앉많옳` (보충, 27자 — 미포함 초성 8개·중성 16개 보강 + 겹받침 5종)
- **도구**: `scripts/editor_server.py`의 `/api/original`이 이미 한글 등 모든 코드포인트에서 동작 — 에디터에 글자를 입력하면(팔레트 없이도) 원본 비트맵 로드·저장 가능. 참조 오버레이(반각 짝이 없는 글자는 자기 자신의 원본을 흐리게 표시)도 지원하도록 수정 완료.
- **PC-98 둥근모꼴 참조**: Light 한글을 그릴 때 두 번째 참조로 PC-98 BIOS 폰트(둥근모꼴)를 겹쳐 본다. 자음 디테일이 원본 도깨비 디나루와 달라서 우리 각진 스타일을 잡는 기준이 됨.
  - 소스: [`gensei-pc98/docs/bios/font.bmp`](../../gensei-pc98/docs/bios/font.bmp) (2048×2048, 1bpp, 16px 그리드). **KS X 1001 완성형 2,350자 전부**가 25열×94행 블록에 **EUC-KR 순서로 열-우선(column-major)** 배치돼 있음: 가 = cell (col 16, row 33), `index=(col-16)*94+(row-33)`, 픽셀 원점 = `col*16, row*16`. (저장소의 `tools/charmap.json`은 게임 텍스트 SJIS 표라 한자 영역을 가리킴 — 글리프 조회에 쓰면 안 됨.)
  - **매칭 기록 파일**: [`tools/pc98_hangul_map.json`](../tools/pc98_hangul_map.json) — 유니코드 음절→`[col,row]` 2,350개. 생성/재현: [`scripts/pc98_hangul_map.py`](../scripts/pc98_hangul_map.py) (2,350자 전부 ROM에 실측 존재, blank 0). 에디터는 `/api/pc98`가 이 파일을 읽어 Light 캔버스에 파란색 오버레이로 표시.
- **진행 상태**: 스타터 세트 확정, 에디터 인프라 준비 완료(원본 회색 + PC-98 둥근모 파란색 이중 오버레이). 실제 드로잉은 미착수.

## 검증 참고

- `scripts/verify_ttf.py`(픽셀-정확 회귀 테스트)는 **손대지 않은 한글에만** 유효하다. Phase 2에서 한글도 변형되므로 그 이후에는 이 테스트 대신 별도 시각 QA + fontbakery로 검증한다.
